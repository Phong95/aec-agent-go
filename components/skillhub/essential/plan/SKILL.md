# Plan

Plan work before you start it, then work through the plan step by step, checking each step, so nothing is skipped and the user can follow along.

## Procedure

1. **Define done.** Restate the goal in one sentence and list what must be true when you finish: deliverables, files, answers.
2. **Look before planning.** Read or search what you need first (files, the sandbox, the web) so the plan rests on facts, not guesses. Keep this short.
3. **Write the plan** as a numbered checklist:
   - Make each step small enough to verify, and name the tool(s) it uses.
   - Note dependencies ("after 2").
   - Mark any irreversible or consequential step (sending, deleting, spending) with ⚠ and get the user's confirmation before doing it.
4. **Share or proceed.** Show the plan and wait for a go-ahead when the task is large, ambiguous or risky, or when the user asked for a plan. Otherwise say it in one line and start.
5. **Execute** one step at a time. After each step, check its result (read back the file, re-run the check) before marking it done: `[x]` done, `[ ]` to do, `[~]` skipped (with the reason).
6. **Re-plan openly.** If a step fails, or you learn something that changes the approach, update the plan and tell the user what changed and why. Don't silently drop steps.
7. **Finish.** Check the result against the definition of done. Report what was done, what wasn't, and any follow-ups.

For long work in a sandbox, keep the plan in `plan.md` in your workspace and update it as you go, so progress survives a long conversation.

## Pitfalls

- Planning so long that you never start. Match the plan's depth to the task.
- Steps like "handle the data" that can't be verified. Name a concrete output for each step.
- Marking a step done without checking its result.
